# PRE-PILOT-007 — протокол калибровки и измерительные инструменты пилота

## Назначение

Пакет подготавливает единый локальный контур сбора доказательств для первого реального пилота. Он нужен для калибровки рабочего процесса, проверки полезности отчёта, разбора расхождений с экспертами и подготовки будущей методологии оценки.

Пакет не обучает и не выбирает модель, не генерирует прогноз и не задаёт финальные пороги качества.

Планируемый объём первого пилота — 15–20 реальных креативов. Такой объём достаточен для проверки процесса и отчётности, но недостаточен для устойчивого обучения модели, обещаний точности или доказательства причинного creative lift.

## Команды

```bash
make pilot-calibration-package

python scripts/pilot_calibration_protocol.py generate --output <dir>
python scripts/pilot_calibration_protocol.py seal --input <dir>
python scripts/pilot_calibration_protocol.py validate --input <dir>
python scripts/pilot_calibration_protocol.py summarize --input <dir>
python scripts/pilot_calibration_protocol.py self-test --output <dir>
python scripts/pilot_calibration_protocol.py check-determinism
```

## Состав пакета

- `calibration_protocol.json` — единицы анализа, порядок экспертного просмотра, политика анализа и границы допустимых выводов;
- `metric_dictionary.csv` — 15 измерений процесса, экспертной полезности, покрытия исходами, опросных прокси и будущей проверки прогнозов;
- `case_register.csv` — 20 строк для регистрации креатива вместе с медиаконтекстом и периодом наблюдения;
- `expert_review.csv` — оценка каждого finding отдельно, включая правильность, релевантность, применимость и прослеживаемость;
- `finding_adjudication.csv` — сохранение и разрешение расхождений между экспертами;
- `outcome_linkage.csv` — связь с историческими или посткампанийными наблюдениями и обязательным SHA-256 provenance;
- `questionnaire_evidence.csv` — раздельный учёт ответов реальных людей и синтетического proxy;
- `workflow_log.csv` — wall-clock time, operator touch time, ручные действия и ошибки;
- `decision_log.csv` — методологические и пилотные решения с принятыми ограничениями;
- `package_manifest.json` — размеры и SHA-256 всех файлов;
- после `summarize`: `calibration_summary.json` и `calibration_summary.md`.

## Единица наблюдения

`case_id` означает не просто изображение, а вариант креатива, связанный с известным медиаконтекстом и окном наблюдения. Платформа, placement, формат, аудитория и кампания могут оставаться пустыми, когда данных нет; система не должна их угадывать.

Включённый case не может оставаться шаблоном. Для него обязательны `creative_id`, исходный `source_record_id` и SHA-256 креатива. Это не позволяет считать заполненной строку без прослеживаемого материала.

## Экспертная проверка

Системный вывод фиксируется до просмотра экспертами. Каждый finding проверяется отдельно. Пропущенная системой проблема добавляется как `finding_origin=human_added`, а не скрывается в общей оценке. Рекомендуются два независимых reviewer, по возможности не видящих кампанийные исходы до первичной оценки. Расхождения сохраняются и затем отражаются в adjudication-регистре.

`expert_supported_finding_rate` является показателем согласия экспертов с findings в конкретном пилоте, а не валидированной точностью модели.

## Исторические данные и опросы

В `outcome_linkage.csv` поле `causal_interpretation_allowed` обязано оставаться `false`. Исторический CTR и иные показатели могут использоваться только как описательное или направленное свидетельство при документированном контексте.

В `questionnaire_evidence.csv` количество real-human и synthetic ответов должно в сумме совпадать с `respondent_count`. Синтетический источник не может содержать ответы реальных людей и наоборот. Estimate обязан находиться внутри заявленной шкалы.

## Итоговый summary

Summary выводит только описательные показатели:

- число включённых реальных и синтетических cases;
- completion rate процесса;
- покрытие реальных cases завершёнными workflow measurements;
- медианы wall-clock, operator touch time и ручных действий;
- finding-level поддержку, actionability и traceability;
- покрытие реальных cases экспертными reviews;
- human-added findings и потенциально вредные false positives;
- disagreement rate после adjudication;
- покрытие историческими наблюдениями;
- real-human и synthetic questionnaire counts раздельно.

Статус `methodology_review_required` появляется только после регистрации не менее 15 реальных cases, наличия finding-level review для каждого из них и завершённого workflow measurement для каждого case. Это всё равно не статус `validated` или `accurate`. Любой внешний вывод требует отдельного согласования владельца методологии, технического владельца и клиента.

## Границы

Пакет не подтверждает:

- точность модели;
- причинный creative lift;
- рыночную эффективность;
- репрезентативность синтетического опроса;
- юридическое, медицинское или регуляторное одобрение;
- достаточность 15–20 cases для обучения production-модели.
